## 🎯 Исполнительное резюме

Multi-Device Sync архитектура для Floktask — это система, которая обеспечивает синхронизацию данных между несколькими устройствами пользователя. Это позволяет:

- **Работать на любом устройстве** с актуальными данными
- **Продолжать работу** с того места, где остановился на другом устройстве
- **Синхронизировать изменения** в реальном времени
- **Разрешать конфликты** автоматически или вручную

Цель: сделать Floktask **кроссплатформенным приложением с бесшовной синхронизацией** между всеми устройствами пользователя.

### Протокол синхронизации

```
┌─────────────────────────────────────────────────────────────┐
│                    Sync Protocol                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Device → Server                                            │
│  ─────────────                                             │
│  1. GET /sync/status?deviceId=XXX&lastSync=YYY            │
│     - Получение статуса синхронизации                       │
│     - Проверка новых изменений на сервере                  │
│                                                             │
│  2. POST /sync/push                                         │
│     - Отправка локальных изменений                          │
│     - Формат: {changes: [...], deviceId: XXX, timestamp: YYY} │
│                                                             │
│  3. GET /sync/pull?since=YYY                                │
│     - Получение изменений с сервера                         │
│     - Формат: {changes: [...], timestamp: YYY}             │
│                                                             │
│  4. POST /sync/ack                                          │
│     - Подтверждение получения изменений                     │
│     - Формат: {changeIds: [...], deviceId: XXX}            │
│                                                             │
│  Server → Device                                            │
│  ─────────────                                             │
│  1. WebSocket / Server-Sent Events                          │
│     - Push уведомления об изменениях                       │
│     - Формат: {type: "change", entity: "task", id: XXX}    │
│                                                             │
│  2. Periodic Polling (fallback)                             │
│     - Периодические запросы на обновления                   │
│     - Интервал: 30 секунд                                   │
└─────────────────────────────────────────────────────────────┘
```

### Модель данных для синхронизации

```kotlin
// Устройство
data class Device(
    val id: String,  // UUID
    val type: DeviceType,  // ANDROID, IOS, WEB
    val name: String,  // User-friendly name
    val lastSync: Instant? = null,
    val status: DeviceStatus = DeviceStatus.ACTIVE
)

enum class DeviceStatus {
    ACTIVE, INACTIVE, DISCONNECTED
}

// Изменение для синхронизации
data class SyncChange(
    val id: String,  // Unique change ID
    val deviceId: String,
    val entityType: EntityType,
    val entityId: String,
    val operation: SyncOperation,
    val data: Map<String, Any>,
    val timestamp: Instant,
    val version: Long,
    val status: ChangeStatus = ChangeStatus.PENDING
)

enum class SyncOperation {
    CREATE, UPDATE, DELETE
}

// Статус синхронизации
data class SyncStatus(
    val deviceId: String,
    val lastSync: Instant? = null,
    val pendingChanges: Int = 0,
    val conflicts: Int = 0,
    val isSyncing: Boolean = false,
    val lastError: String? = null
)

// Конфликт
data class SyncConflict(
    val id: String,
    val entityType: EntityType,
    val entityId: String,
    val deviceChanges: List<SyncChange>,
    val serverData: Map<String, Any>? = null,
    val resolution: ConflictResolution? = null,
    val createdAt: Instant = Instant.now()
)

enum class ConflictResolution {
    USE_LOCAL, USE_SERVER, MERGE, MANUAL
}
```

### Алгоритм синхронизации

```
1. Инициализация синхронизации
   ├─ Проверка подключения к сети
   ├─ Получение текущего статуса с сервера
   └─ Проверка локальных изменений

2. Отправка локальных изменений
   ├─ Выборка изменений со статусом PENDING
   ├─ Группировка по типу сущности
   ├─ Сжатие данных
   └─ Отправка на сервер (POST /sync/push)

3. Обработка ответа сервера
   ├─ Обновление статуса отправленных изменений
   ├─ Применение серверных изменений к локальной базе
   └─ Обновление версии данных

4. Получение серверных изменений
   ├─ Запрос изменений с последней синхронизации
   ├─ Фильтрация уже полученных изменений
   └─ Применение к локальной базе

5. Разрешение конфликтов
   ├─ Обнаружение конфликтов (одинаковый entityId, разные version)
   ├─ Автоматическое разрешение (если возможно)
   └─ Сохранение конфликта для ручного разрешения

6. Обновление статуса синхронизации
   ├─ Обновление lastSync timestamp
   ├─ Очистка очереди изменений
   └─ Уведомление UI о завершении
```

### Разрешение конфликтов

**Стратегия 1: Version Vector (Vector Clocks)**
```
Для каждой сущности хранится вектор версий:
{deviceA: version1, deviceB: version2, ...}

При конфликте:
- Сравниваются векторы версий
- Если один вектор доминирует (все версии >=), используется он
- Иначе - конфликт требует разрешения
```

**Стратегия 2: Last Write Wins с timestamp**
```
Для каждой сущности хранится:
- timestamp последнего изменения
- deviceId устройства

При конфликте:
- Сравниваются timestamp
- Используется изменение с более поздним timestamp
- При одинаковом timestamp - конфликт
```

**Стратегия 3: Ручное разрешение**
```
Для критических конфликтов:
- Сохраняются обе версии
- Пользователь выбирает, какую сохранить
- Или объединяет изменения вручную
```

**Рекомендация:**
- Использовать Version Vector для большинства случаев
- Last Write Wins для простых сущностей
- Ручное разрешение для критических данных

## ⚠️ Риски

| Риск | Вероятность | Влияние | Меры по снижению |
|------|-------------|---------|------------------|
| Потеря данных при синхронизации | Низкая | Критическое | Транзакционность, резервное копирование |

| Несовместимость между версиями | Средняя | Высокое | Версионирование API, миграции |

## 📝 Примечания

1. **Синхронизация ≠ Резервное копирование:** Синхронизация - это обмен изменениями, резервное копирование - это сохранение данных
2. **Offline-First:** Все функции должны работать без интернета
3. **Конфликты:** Минимизировать количество конфликтов через хороший дизайн
4. **Производительность:** Синхронизация не должна мешать работе пользователя
5. **Безопасность:** Все данные шифруются при передаче и хранении
