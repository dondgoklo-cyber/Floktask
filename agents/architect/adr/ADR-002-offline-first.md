# ADR-002: Offline-First Подход для Floktask

## 📅 Методология
- **Статус:** Accepted
- **Дата:** 2026-09-06
- **Автор:** Architect
- **Участники:** Product Manager, Backend, Frontend

## 🎯 Контекст и проблема

### Контекст
Floktask должен работать в условиях нестабильного интернет-соединения и предоставлять пользователю полный функционал в оффлайн-режиме. Это критично для мобильных приложений, где пользователи могут находиться в местах с плохим покрытием сети.

Текущая реализация использует Room для локального хранения, но не имеет механизма синхронизации с сервером.

### Проблема
- ❌ Нет синхронизации между устройствами
- ❌ Изменения теряются при отсутствии интернета
- ❌ Конфликты между оффлайн и онлайн изменениями
- ❌ Нет механизма разрешения конфликтов

### Драйверы (что нас мотивирует)
- **Пользовательский опыт** — Пользователи ожидают, что приложение будет работать без интернета
- **Надежность** — Никакие изменения не должны теряться
- **Синхронизация** — Все устройства должны иметь актуальные данные
- **Конкурентоспособность** — Todoist и TickTick поддерживают offline-first

## ⚖️ Варианты решения

### Вариант 1: Client-Server Sync с Queue
Классическая модель: клиент отправляет изменения на сервер, сервер синхронизирует с другими клиентами.

**Плюсы:**
- ✅ Простота реализации
- ✅ Централизованное управление данными
- ✅ Легко отслеживать изменения

**Минусы:**
- ❌ Зависимость от сервера
- ❌ Конфликты при оффлайн-изменениях
- ❌ Задержка синхронизации

**Оценка:**
- **Сложность реализации:** Medium
- **Стоимость:** $$
- **Время:** 2 недели
- **Риск:** Medium

### Вариант 2: Conflict-Free Replicated Data Types (CRDT)
Использование CRDT для автоматического разрешения конфликтов.

**Плюсы:**
- ✅ Автоматическое разрешение конфликтов
- ✅ Нет необходимости в центральном сервере
- ✅ Высокая доступность

**Минусы:**
- ❌ Высокая сложность реализации
- ❌ Ограниченные типы данных
- ❌ Сложность отладки

**Оценка:**
- **Сложность реализации:** High
- **Стоимость:** $$$$
- **Время:** 6-8 недель
- **Риск:** High

### Вариант 3: Operational Transformation (OT)
Использование OT для синхронизации операций (как в Google Docs).

**Плюсы:**
- ✅ Точное разрешение конфликтов
- ✅ Поддержка сложных операций
- ✅ Реальное время синхронизации

**Минусы:**
- ❌ Очень высокая сложность
- ❌ Требования к производительности
- ❌ Сложность масштабирования

**Оценка:**
- **Сложность реализации:** Very High
- **Стоимость:** $$$$$
- **Время:** 3+ месяца
- **Риск:** Very High

### Вариант 4: Event Sourcing + CQRS
Хранение всех изменений как событий, воспроизведение состояния.

**Плюсы:**
- ✅ Полная история изменений
- ✅ Возможность отката
- ✅ Масштабируемость чтения

**Минусы:**
- ❌ Высокая сложность
- ❌ Требования к хранилищу
- ❌ Сложность миграции

**Оценка:**
- **Сложность реализации:** High
- **Стоимость:** $$$$
- **Время:** 4-6 недель
- **Риск:** High

## 🎯 Выбранное решение
**Client-Server Sync с Queue + Conflict Resolution Strategy**

### Архитектура

```
┌─────────────────────────────────────────────────────────────┐
│                      Mobile Client                            │
│  ┌─────────────┐    ┌─────────────┐    ┌─────────────────┐  │
│  │ Local DB    │    │ Sync Queue  │    │ Conflict        │  │
│  │ (Room)      │◄───►│ (Pending)    │◄───►│ Resolution      │  │
│  └─────────────┘    └─────────────┘    └─────────────────┘  │
└─────────────────────────────────────────────────────────────┘
                              │
                              │ Sync API
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                      Sync Service                             │
│  ┌─────────────┐    ┌─────────────┐    ┌─────────────────┐  │
│  │ Change      │    │ Conflict     │    │ Version         │  │
│  │ Queue       │    │ Detector     │    │ Manager         │  │
│  └─────────────┘    └─────────────┘    └─────────────────┘  │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                     Main Database                            │
│                  (PostgreSQL)                                │
└─────────────────────────────────────────────────────────────┘
```

### Компоненты

#### 1. Local Database (Room)
- Хранит все данные локально
- Схемы: Tasks, Projects, Users, etc.
- Версионирование данных (version vector)

#### 2. Sync Queue
- Очередь изменений для синхронизации
- Статусы: PENDING, SYNCING, SYNCED, FAILED
- Приоритезация изменений

#### 3. Change Tracker
- Отслеживает все локальные изменения
- Создает change events
- Добавляет в sync queue

#### 4. Sync Manager
- Отправляет изменения на сервер
- Получает изменения с сервера
- Управляет конфликтами

#### 5. Conflict Resolution
- **Стратегия 1: Last Write Wins** — Последнее изменение побеждает
- **Стратегия 2: Manual Resolution** — Пользователь выбирает
- **Стратегия 3: Merge** — Автоматическое слияние (для некоторых типов)

### Sync Protocol

```
1. Client → Server: GET /sync?since={lastSyncTimestamp}
   - Получает изменения с сервера
   
2. Server → Client: 200 OK {changes: [...], version: X}
   - Сервер отправляет изменения
   
3. Client: Применяет изменения локально
   - Обновляет local DB
   - Разрешает конфликты
   
4. Client → Server: POST /sync {changes: [...], version: Y}
   - Отправляет локальные изменения
   
5. Server: Применяет изменения
   - Обновляет main DB
   - Отправляет подтверждение
   
6. Server → Client: 200 OK {applied: [...], conflicts: [...]}
   - Подтверждение или конфликты
```

### Data Versioning

Каждая сущность имеет:
- `id` — Уникальный идентификатор
- `version` — Версия данных (timestamp или vector clock)
- `createdAt` — Время создания
- `updatedAt` — Время последнего обновления
- `deletedAt` — Время удаления (soft delete)

### Conflict Detection

Конфликт обнаруживается, когда:
- Две сущности имеют одинаковый `id`
- Но разные `version`
- И обе были изменены после последней синхронизации

### Conflict Resolution Strategies

| Тип данных | Стратегия | Описание |
|-----------|----------|----------|
| Задачи | Last Write Wins | Последнее изменение побеждает |
| Проекты | Manual Resolution | Пользователь выбирает |
| Настройки | Client Wins | Локальные настройки приоритетны |
| Метки | Merge | Объединение списков |

## 📊 Последствия

### Положительные
- ✅ Полная работа в оффлайн-режиме
- ✅ Автоматическая синхронизация при появлении интернета
- ✅ Нет потери данных
- ✅ Поддержка multi-device sync
- ✅ Хороший пользовательский опыт

### Отрицательные
- ⚠️ Увеличение сложности клиента
- ⚠️ Необходимость обработки конфликтов
- ⚠️ Увеличение трафика
- ⚠️ Задержка синхронизации

### Нейтральные
- 🔹 Необходимость тестирования синхронизации
- 🔹 Увеличение размера локальной БД

## 📝 Примечания
- **Offline-first** — Все операции сначала выполняются локально, затем синхронизируются
- **Optimistic UI** — Интерфейс обновляется сразу, синхронизация в фоне
- **Background Sync** — Синхронизация происходит в фоне при наличии интернета
- **Manual Sync** — Пользователь может запустить синхронизацию вручную
- **Sync Status** — Показываем статус синхронизации пользователю
