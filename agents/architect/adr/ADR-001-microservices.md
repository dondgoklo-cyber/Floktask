# ADR-001: Микросервисная Архитектура для Floktask

## 📅 Методология
- **Статус:** Accepted
- **Дата:** 2026-09-05
- **Автор:** Architect
- **Участники:** Product Manager, Backend, Frontend

## 🎯 Контекст и проблема

### Контекст
Текущая архитектура Floktask представляет собой монолитное Android-приложение с локальным хранилищем Room. Для масштабирования до уровня конкурентов (Todoist, TickTick) и поддержки мультиплатформенности (Android, iOS, Web) требуется переход на серверную архитектуру.

Проект развивается 5 ИИ-агентами:
1. **Product Manager** — управляет требованиями
2. **Architect** (ты) — проектирует систему
3. **Backend** — реализует серверную часть
4. **Frontend** — разработка клиентских приложений
5. **Orchestrator** — координирует работу

### Проблема
Монолитная архитектура имеет следующие ограничения:
- ❌ Нет возможности синхронизации между устройствами
- ❌ Ограниченная масштабируемость
- ❌ Сложность добавления новых функций
- ❌ Нет кроссплатформенности
- ❌ Сложность тестирования и развертывания

### Драйверы (что нас мотивирует)
- **Масштабируемость** — Поддержка миллионов пользователей
- **Кроссплатформенность** — Android, iOS, Web
- **Синхронизация** — Multi-device sync с offline-first
- **Гибкость** — Независимое развитие компонентов
- **Надежность** — Отказоустойчивость и высокая доступность

## ⚖️ Варианты решения

### Вариант 1: Монолитный Backend
Создать один backend-сервис на Spring Boot с REST API.

**Плюсы:**
- ✅ Простота разработки и развертывания
- ✅ Быстрый старт
- ✅ Легко тестировать
- ✅ Низкие инфраструктурные затраты

**Минусы:**
- ❌ Ограниченная масштабируемость
- ❌ Сложность поддержки разных доменов
- ❌ Риск single point of failure
- ❌ Сложность команды (все должны знать весь код)

**Оценка:**
- **Сложность реализации:** Medium
- **Стоимость:** $$
- **Время:** 2-3 недели
- **Риск:** Medium

### Вариант 2: Микросервисная Архитектура
Разделение на независимые сервисы по бизнес-доменам.

**Плюсы:**
- ✅ Высокая масштабируемость
- ✅ Независимое развитие команд
- ✅ Технологическая гибкость
- ✅ Отказоустойчивость
- ✅ Легкость тестирования отдельных компонентов

**Минусы:**
- ❌ Высокая сложность разработки
- ❌ Затраты на инфраструктуру
- ❌ Сложность отладки
- ❌ Необходимость координации между сервисами

**Оценка:**
- **Сложность реализации:** High
- **Стоимость:** $$$$
- **Время:** 4-6 недель
- **Риск:** High

### Вариант 3: Modular Monolith
Модульный монолит с четкими границами между модулями.

**Плюсы:**
- ✅ Простота развертывания
- ✅ Четкие границы между модулями
- ✅ Легкость тестирования
- ✅ Возможность последующего разделения на микросервисы

**Минусы:**
- ❌ Ограниченная масштабируемость
- ❌ Сложность поддержки больших модулей
- ❌ Не полная изоляция

**Оценка:**
- **Сложность реализации:** Medium
- **Стоимость:** $$
- **Время:** 3-4 недели
- **Риск:** Medium

## 🎯 Выбранное решение
**Микросервисная Архитектура** с постепенным переходом от монолита.

### Структура сервисов

```
┌─────────────────────────────────────────────────────────────┐
│                        API Gateway                            │
│                  (Spring Cloud Gateway)                      │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                      Service Mesh                             │
│                   (Istio / Linkerd)                           │
└─────────────────────────────────────────────────────────────┘
                              │
    ┌─────────────────┬─────────────────┬─────────────────┐
    ▼                 ▼                 ▼                 ▼
┌─────────────┐ ┌─────────────┐ ┌─────────────┐ ┌─────────────┐
│  User       │ │  Task       │ │  Project    │ │  Sync       │
│  Service    │ │  Service    │ │  Service    │ │  Service    │
└─────────────┘ └─────────────┘ └─────────────┘ └─────────────┘
    │                 │                 │                 │
    ▼                 ▼                 ▼                 ▼
┌─────────────┐ ┌─────────────┐ ┌─────────────┐ ┌─────────────┐
│ PostgreSQL  │ │ PostgreSQL  │ │ PostgreSQL  │ │   Redis     │
│ (Users)     │ │ (Tasks)     │ │ (Projects)  │ │  (Sync Q)   │
└─────────────┘ └─────────────┘ └─────────────┘ └─────────────┘

┌─────────────────┐
│   AI Service    │ ←─┐
└─────────────────┘   │
                     ├─ External AI Providers (Gemini, Yandex GPT)
┌─────────────────┐   │
│ Notification     │ ←─┘
│ Service          │
└─────────────────┘
    │
    ▼
┌─────────────────┐
│   Push Service   │
│  (FCM/APNS/Web)  │
└─────────────────┘
```

### Сервисы и их ответственность

| Сервис | Ответственность | Технологии | База данных |
|--------|----------------|------------|--------------|
| **API Gateway** | Маршрутизация, аутентификация, rate limiting | Spring Cloud Gateway | - |
| **User Service** | Регистрация, аутентификация, профили | Spring Boot | PostgreSQL |
| **Task Service** | Управление задачами, подзадачами, тегами | Spring Boot | PostgreSQL |
| **Project Service** | Управление проектами, досками | Spring Boot | PostgreSQL |
| **Sync Service** | Синхронизация данных, конфликты | Spring Boot | PostgreSQL + Redis |
| **AI Service** | Интеграция с AI, генерация подсказок | Spring Boot | - |
| **Notification Service** | Уведомления, reminders | Spring Boot | PostgreSQL |

### Коммуникация между сервисами

1. **Синхронная** (REST API) — для запросов, требующих немедленного ответа
2. **Асинхронная** (Kafka/RabbitMQ) — для событий и background-операций
3. **gRPC** — для внутренней коммуникации между сервисами

### API Gateway
- **Spring Cloud Gateway** — основной шлюз
- **Маршрутизация** на основе path и headers
- **Аутентификация** через JWT
- **Rate limiting** для защиты от перегрузок
- **Circuit breaker** для отказоустойчивости

## 📊 Последствия

### Положительные
- ✅ Высокая масштабируемость — каждый сервис можно масштабировать независимо
- ✅ Технологическая гибкость — разные сервисы могут использовать разные технологии
- ✅ Независимое развитие — команды могут работать над разными сервисами параллельно
- ✅ Отказоустойчивость — падение одного сервиса не влияет на остальные
- ✅ Легкость тестирования — каждый сервис можно тестировать изолированно

### Отрицательные
- ⚠️ Высокая сложность разработки — необходимо координировать работу между сервисами
- ⚠️ Затраты на инфраструктуру — необходимо поддерживать несколько сервисов
- ⚠️ Сложность отладки — необходимо отслеживать запросы через несколько сервисов
- ⚠️ Задержка сети — дополнительные хопы между сервисами

### Нейтральные
- 🔹 Необходимость обучения команды — работа с микросервисами требует новых навыков
- 🔹 Изменение подхода к тестированию — необходимо тестировать интеграции между сервисами

## 📝 Примечания
- **Постепенный переход**: Начинаем с монолита, затем разделяем на сервисы по мере роста
- **Service Mesh**: Используем Istio для управления трафиком и наблюдения
- **Observability**: Centralized logging (ELK), metrics (Prometheus + Grafana), tracing (Jaeger)
- **CI/CD**: Автоматизированное тестирование и развертывание для каждого сервиса
